# Binary re-read: 2.1.258 → 2.1.280 loader diff

Date: 2026-09-22. SDK 0.3.280 / bundled CLI 2.1.280, diffed against the
2.1.258 binary the loader was ported from. Status: DONE — source reading
plus the p20-kill1-later wire probe, which confirmed the tail rule.

## Why

The 0.3.280 suite run showed one loader-side drift inside clauctl's fixture
space (p20-kill1 healed instead of cut; FINDINGS "Version drift"). The
loader's heal rule was inferred from that single wire shape. This reading
checks the whole load pipeline against the new binary so the rule — and
every other stage — rests on source, not on one probe.

## Technique

Binary: `node_modules/@anthropic-ai/claude-agent-sdk-linux-x64/claude`
(JS embedded as plain text). Minified names change per build AND collide
across chunks — a `grep -boa` for a short name returns unrelated functions
first; filter hits to offset > 150,000,000 (the CLI chunk) and, for the
loader in 2.1.280, > 201,000,000. Telemetry string literals (`tengu_*`)
are the stable anchors. Dump windows with
`dd if=… bs=1 skip=N count=M | sed 's/;/;\n/g'` into
`/tmp/clauctl-bin-2.1.280/*.js`; for a structural diff, normalize
identifiers (`sed -E 's/[A-Za-z_$][A-Za-z0-9_$]*/X/g'`) and diff windows
cut at the same byte offset relative to a shared anchor — windows cut at
different function boundaries produce spurious diffs. `$`-prefixed names
survive the normalizer as `$X` and show up as noise.

## Per-stage diff

### Stages 1–2 (relink, walk, fold finish, leaf pick): identical

Token-identical after identifier normalization. Nothing to re-derive.

### Stage 3 (expansion): changed, order-equivalent on native shapes

- Sort key is now file index and the splice interleaves over the group's
  on-chain span rather than inserting after the group's last on-path
  assistant. For the shapes the CLI writes (calls chained, results
  branching, continuation on the last-written result) the resulting order
  is the same as before.
- New "recovered tails" pass (`k8t`/`w8t`): attachment, non-boundary
  system, and isMeta user chains hanging off group members or their
  results are pulled back in. Our loader does not model this; it only
  affects entries the loaded-context consumers filter anyway (edge shape,
  not modeled — see Consequences).

### Stage 4 (resume sanitizers): heal is new, and it is tail-conditioned

- `lRe` body identical to `gEe`; one option renamed
  (`outSupersededToolUseIds` → `outTrailingUnresolvedToolUseIds`).
- `v3t` ≡ `rfe`: drop a thinking-only assistant entry unless a
  same-message-id sibling has non-thinking content, or
  preserveTrailingThinking applies to the last entry, or the
  resumedFromIncompleteThinking exception holds. `w3t` ≡ `nfe`
  (whitespace-only drop). Both versions run them right after the
  sanitizer at the resume entry; 280 loops to a fixed point and passes
  `mergeAdjacentUsers:false` where 258 merged unconditionally.
- The resume entry in 280:

  ```
  Xe=lRe(_e,n,Ue&&!He?{dropSiblingBlocks:!0,…,shutdownUnwindResultsDoNotResolve:!0}
                     :{outTrailingUnresolvedToolUseIds:$e}),
  ht=$te(Xe), pt=…wDe(ht,xe.size>0)
  …
  else if(gt.kind==="interrupted_turn"){ if($e.size>0) ht=wOr(_e,n,$e), Bn=$e; … }
  ```

  `$e` (the trailing unresolved set) is collected by scanning back from
  the file tail to the last plain user prompt. `wOr(e,n,r)`:
  `s=$te(lRe(e,new Set([...n??[],...r])))`, then for each kept tool_use in
  `r` push a synthetic `is_error` tool_result "[Request interrupted by user
  for tool use]". 258's else-branch passed `void 0` (no trailing set) and
  its `interrupted_turn` branch only appended "Continue from where you left
  off." — no heal.

So the heal applies to unresolved calls in the FILE'S TRAILING TURN only.
A half-answered group followed by later user turns still has its dead
call dropped block-level in 280, exactly as in 258. The "a group with at
least one answered call keeps every call" rule that FINDINGS §4, the specs
and `sanitizeForResume`/`ToolGroup.excludedAtEnd` state after the 0.3.280
suite run is a mis-generalization of p20-kill1, whose file ends at the
answered result — that shape cannot distinguish "group has an answer" from
"call is in the trailing turn". (Why kill0 still drops: with zero results
the whole group is unresolved; `lRe` removes those blocks before `wOr`
could heal them, same as 258.)

### Two-pass byte reader (both versions; files > 5 MiB only)

Runs only when the file exceeds `5242880` bytes and `keepAllLeaves` is
false — true for the resume path (`oHe→khe(path,{precedingEntries})`); a
leafUuids/tree caller passes `keepAllLeaves:true`. Pass 1 scans
uuid/parentUuid/isSidechain/compact_boundary bytes (a boundary without
preservedSegment resets the tables = the stage-1 cut), walks ancestry from
the last non-sidechain row ∪ the `last-prompt` leafUuid (a phantom parent
falls back to loading all rows, telemetry `tengu_transcript_phantom_parent`).
Pass 2 parses only those rows in 258; 280 additionally admits
same-message-id assistant siblings (`x8t`/`R8t` propagate the api message
id), progress rows (`H0e`), and tails (`k8t`/`w8t`) beneath loaded rows —
so large files now feed expansion the same inputs small files do. Every
probe and fixture is ≤ 5 MiB and takes the full-parse path in both
versions; this reader remains an untested consumer (FINDINGS "Consumer
scoping").

### Stage 5 (tool-pair repair) and row repair

`IAt` additionally drops `tool_result` blocks found inside assistant
messages (`Z$e`) and excludes them from the server-tool id set; otherwise
identical to `IVn`. `r$t` (new) edits `stop_hook_summary`/system row
fields and drops rows whose message is invalid (`ZFt`/`e$t`); it does not
change chain shape.

## Consequences

- Wire probe `p20-kill1-later` (kill1's file + a later user turn and its
  reply; pre-registered models tail-heal-only / group-heal / stage5-heal):
  one run, `tail-heal-only` — callB absent, no synthetic result of either
  wording, later turn present; kill1 re-confirmed `kept-healed-interrupt`
  in the same run. Pinned in check-reports.mjs.
- Product model corrected to the positional rule: `sanitizeForResume`
  (src/core/tree/loader.ts) heals only the group the chain ends in when
  the chain's last entry is a tool result; `ToolGroup.excludedAtEnd(
  atFileEnd)` (tree/tool-group.ts) keeps unanswered calls only at file end
  with the group's last row a result — the live tree, which never
  finishes, excludes a group's dead calls when a later entry ends it.
  Approximation: the CLI's scan stops at the last plain user PROMPT; ours
  ends the group at any non-member entry (an attachment after the result
  would differ — not a shape probed).
- Stage-3 recovered tails: proposed NOT modeled (edge shape; the entries it
  recovers are filtered by every loaded-context consumer).
- `loader.ts` header provenance updated: stages 1–2 verified identical
  against 2.1.280 by this reading; stage 3 order-equivalent; stage 4 per
  above.
