# Plan: loader round 2 — API-message expansion, resume path, request normalization

Date: 2026-08-28. SDK 0.3.250 / bundled CLI 2.1.250. Status: DRAFT (pending
reviewer hardening; experiments not yet run).

## Why

The tui-parity work surfaced a session where two parallel tool calls (Grep +
Glob) were split across sibling transcript entries sharing one API
`message.id`, with only one sibling on the `parentUuid` path to the leaf — yet
both `getSessionMessages` and a live `--resume` showed the model seeing all of
them. Our loader model (`src/core/tree/loader.ts` `loadedContext`, ported from
the 2.1.170 binary; FINDINGS.md; the claude-context blog post) treats the
context as a pure parent walk, so it under-reports these in-turn forks. In-turn
forks are common (three found across two tui-parity scenario sessions).

Separately, Anton observed that when a boundary preserves several user
messages in a row, the context the assistant actually receives drops some of
them — a request-time normalization our model doesn't cover.

Goals: pin the actual 2.1.250 behavior from source + wire evidence, roll it
into FINDINGS.md (living document), re-derive `docs/specs/session-tree.md`
"Ground truth", then (separately) spec the clauctl changes and fix the blog
post.

## Phase 0 findings: source reading (done 2026-08-28, informs the probes)

All from the bundled binary `node_modules/@anthropic-ai/claude-agent-sdk-linux-x64/claude`
(v2.1.250, JS embedded as plain text; byte offsets noted for re-dumping) and
the plain-JS `sdk.mjs`. Minified names cited so regions can be relocated.

### getSessionMessages (sdk.mjs `Uq→Fq→Kje→Wje`; binary copy at ~195,003,000 `qr`/`Br`)

1. Filter to typed entries with uuids; uuid→entry Map (duplicate file uuids:
   last wins).
2. Relink pass over **every** compact_boundary in map order (NOT
   last-boundary-only): skip a boundary (`continue`) when `uuids` is empty or
   any uuid is absent from the file. **No duplicate-uuid check.** Chain
   rewrite (`uuids[0].parent = anchor`, chain) + anchor-child reparent
   (every child of anchor except `uuids[0]` → `uuids.last()`). Legacy
   `preservedSegment` handled analogously. **No cut step** — exclusion of
   non-preserved pre-boundary entries falls out of the leaf walk only.
3. Leaf selection: dangling tips of the relinked relation, each climbed to
   the nearest user/assistant; prefer non-sidechain/teamName/isMeta; pick the
   max-file-index candidate. Walk from it, reverse.
4. **`Wje` — API-message expansion** (the rule we guessed, confirmed): for
   each on-path assistant `message.id`, splice in (a) all same-id assistant
   siblings not already on the path, (b) the tool_result-bearing user
   children of _all_ entries of that message — each group timestamp-sorted,
   siblings before results, inserted right after the last on-path entry with
   that id.
5. Output filter: user/assistant (+system only with includeSystemMessages);
   drop isMeta/isSidechain/teamName.

### Resume loader (binary: `F9`=loadTranscriptFile @183,238,827; fold `H0t` @183,232,016; `jGe` @~183,198,900; chain builder `uye` @183,191,741)

- `H0t` fold: uuid→entry map + per-session metadata + `leafUuids` (tips
  analysis with `last-prompt` marker preference; parent-cycle telemetry). **No
  relink in the fold.** Boundaries only reset ancillary state. Files >5 MB
  stream through a pre-boundary **skip** (`dropPreBoundaryEntries`,
  disableable via `CLAUDE_CODE_DISABLE_PRECOMPACT_SKIP`) unless the last
  boundary has preserved metadata (`hasPreservedSegment` scan @~175,256,000).
- `jGe`: leaf = last entry in `leafUuids` (else last non-sidechain), then
  `uye(messages, leaf)`.
- `uye`: parent walk from leaf (cycle guard; **timestamp-fallback repair**
  `Cer` — a broken parent link falls back to the nearest earlier entry within
  5 s with matching isSidechain, telemetry `tengu_chain_timestamp_fallback`),
  reverse, then **`Aer` = an API-message expansion whose code body matches
  `Wje`** (telemetry `tengu_chain_parallel_tr_recovered`; the entry sets and
  downstream normalization the two run over may still differ), then `wer` =
  BFS append of non-user/assistant descendants of the leaf
  (timestamp-sorted).
- **Open**: `uye` performs NO boundary relink, yet round 1's P7 wire
  captures prove preserved messages reach the API on resume — so
  re-insertion happens downstream of (or instead of) this path. Note the
  boundary entry survives in `uye`'s output as an in-memory marker, the same
  shape live compaction produces (`bQ`: `[boundaryMarker, summary,
  messagesToKeep, …]`), so a downstream boundary-aware pass is structurally
  plausible; alternatively `jGe` serves the resume-picker/session-info path
  and the conversation-resume loader is a still-unfound site.
  The only re-insertion code found: `cyn`/`yQ` (@~180,929,400) — a
  sequential pass that, at a boundary, pulls `preservedMessages.allUuids ??
  uuids` (note: **allUuids preferred** — the _unfiltered_ list) and
  re-inserts them after the anchor; all located callers are live-stream
  bookkeeping (subagent/fork/background loops, 4-arg form with a fallback
  entry list). Where the resume path runs it (or an equivalent) is the main
  remaining extraction target.

### Compaction writer (binary: `jme` @~181,878,300; `tIe`/`Ver`/`F$` @~183,255,500)

- `preservedMessages.uuids` = messagesToKeep filtered by `tIe`:
  drops progress entries, empty hook_success attachments, an attachment-type
  denylist, strips one specific tool's tool_use/tool_result blocks, and
  de-virtualizes; `allUuids` = the unfiltered list. So `uuids` vs `allUuids`
  is a _filtered/unfiltered_ pair, and different consumers prefer different
  halves (`cyn` and the fork-context filter @~187,208,000 prefer `allUuids`).
- A cap exists somewhere on the persistence path: preserved uuids truncated
  to the last 1536 (`Q` @~194,101,100).
- `tIe` does NOT drop plain user messages → the consecutive-user drop Anton
  observed is not authored into `uuids`; the loss occurs somewhere after
  `uuids` authoring — resume reconstruction, transcript→API conversion, or
  final request normalization (E2b/p12 discriminate).

## E2a results (2026-08-28, agent-traced; E2c answered)

The resume relink exists and was hiding in `H0t`'s `finish` callback:
`finish:()=>fn(Ser(t))`. **`Ser` @183,189,805** (helper `ker`) mutates the
uuid→entry map BEFORE leaf selection and `uye`'s walk — no downstream
re-insertion; `cyn`/`yQ` is live-stream bookkeeping only (both remaining
sites ruled out: inProcessRunner streaming loop). Call graph: all three
resume entries (interactive `--resume`, `--continue`, headless/SDK `h_`
@~197,270,700) converge on `U5` @~180,718,300 → `B9`/`KIe` → `F9`/`H0t`;
`jGe` is the session-picker side. After the walk: `Bjn` (resume
sanitizers, no boundary logic) → main loop `Ix` @181,746,141 →
`callModel` → `NWn` @182,288,818 (normalization; `Iw` @183,010,295 is the
tool-pair normalizer — E2b digs here).

`Ser` semantics (E2c, verbatim-verified):

- **Last-boundary-only**: scans for the last boundary carrying
  `preservedMessages`/`preservedSegment` metadata; relinks only when that
  IS the file's last boundary. Earlier boundaries' playlists are never
  consulted. (D2 for resume: last-wins. getSessionMessages stays
  sequential-all — a per-consumer divergence.)
- **Stale metadata** (metadata boundary not last): no relink, but the
  pre-last-boundary prune still runs with an empty keep-set — a wipe.
- **Invalid playlist** (uuid missing from file): telemetry
  `tengu_relink_walk_broken`, then return with the map UNTOUCHED — no
  relink, no prune. Preserved messages become unreachable from the leaf;
  the walk follows raw parents and stops at the last null-parent boundary
  entry it reaches. (D5 for resume: abort-untouched, 2.1.170-style —
  NOT getSessionMessages' per-boundary `continue`, NOT our wipe.)
- **No duplicate-uuid check** (D4: the P3 m4 "skip" observation needs the
  p14 re-test; the check exists on neither 2.1.250 path).
- **On success**: chain rewrite (head→anchor, then chained); anchor's
  other children → playlist tail; `usage` token fields ZEROED on preserved
  assistant entries (new fact); **the cut exists here** — every
  pre-boundary entry not on the playlist is deleted from the map, and
  surviving children of deleted entries repoint to the playlist tail
  (D3 for resume: cut + orphan reparent, matching our model;
  getSessionMessages has no cut — p16's two consumers should now give
  DIFFERENT answers, making it a strong probe).

Net: the resume path is much closer to our 2.1.170-derived loadedContext
than the getSessionMessages pipeline is — same last-boundary/cut/
anchor-child/orphan-reparent skeleton; divergences are invalid-playlist
handling (abort-untouched vs our wipe), the post-walk API-message
expansion (`Aer`), usage zeroing, and the timestamp repair (deferred D6).
Open edges: `oJe` REPL hydration inferred from call shape; the 1536-uuid
`Q` presumed writer-side; `hvt`/`Ose`/`Mse` unread (E2b).

## E2b results (2026-08-28, agent-traced)

Request pipeline (offsets verified by excerpt): `mbt` prepend-reminder →
`NWn` @182,288,818 → `hvt` (strip cross-model thinking blocks) → `Iw`
@183,010,295 (drop isVirtual/progress; taskDelivery splice; media heal;
**merge adjacent users `$oe`; merge same-id assistants `DJn`**; then
`Ose`/`aZn`/`Mse`/`lZn` tails) → `B4` → `_vt` @183,091,025 (tool-pair
repair) → `GEe`/`CWn` → wire `uvt`.

- **NO consecutive-user drop rule exists.** Adjacent user messages are
  MERGED into one API user message with all content concatenated (`$oe`;
  tool_results hoisted first by `UNt`; also `Mse` at resume). Nothing is
  lost. The only pipeline stages that delete user entries: `isVirtual`,
  `taskDelivery` splicing (content transformed, not lost), all-media heal
  (can't fire with a text block). The round-1 "consecutive users get
  dropped" observation is either message-count merging (content intact as
  blocks) or has an upstream cause — p12 characterizes on the wire.
- **Same-`message.id` assistant entries regroup into one API message**,
  with the group broken by any intervening non-assistant,
  non-tool-result-user message — a plain user prompt splits a same-id
  pair into separate assistant messages.
- **Tool-pair repair (`_vt`)**: tool_use missing its result → synthetic
  `"[Tool result missing due to internal error]"` is_error result
  prepended to the next user (strict-mode flag throws instead); orphan
  tool_result → block dropped (message dropped if emptied); partial
  parallel groups → healed per-id, nothing dropped; duplicate tool_use
  ids removed.
- **Resume-side sanitizer `eye`** @183,025,825 (U5's `w9` site, NOT in
  the request pipeline): drops WHOLE assistant messages whose tool_uses
  are all unresolved — the predicted fate of a playlist that keeps a tool
  call without its result (vs `_vt` healing it later; wire-discriminable:
  absent vs present-with-synthetic-result).

### Source-predicted E3 outcomes (pre-registration inputs)

- p11a/p11b: on resume, `Ser`'s CUT deletes pre-boundary entries not on
  the playlist BEFORE `Aer` expansion runs — the excluded sibling is gone
  from the map, so expansion cannot recover it. Predict: sibling absent
  from the wire; getSessionMessages (no cut) keeps it. This is exactly
  P8's observed divergence, now explained. Set-context implication if
  confirmed: playlists MUST close over whole API messages; the loader
  will not repair the split.
- p12: predict one merged user API message carrying all three markers.
- p13: predict off-path fork sibling + result on the wire (no boundary →
  no cut → expansion applies).
- p14: `Ser` has no dup check; a `[A,B,A,B]` playlist rewrite leaves an
  A↔B parent cycle — predict cycle-guard truncation, distinct from an
  explicit-skip prediction; exact chains computed when the fixture is
  written.
- p15(a): predict abort-untouched (raw-parent walk stopping at the last
  reachable null-parent boundary), NOT wipe, NOT earlier-boundary relink.
- p16: predict consumer split — resume cuts + reparents the orphan to the
  playlist tail; getSessionMessages follows the raw parent.
- p17 (NEW, +1 call): playlist keeps a tool_use entry but not its
  tool_result. Predict `eye` drops the whole assistant message at resume
  load; alternative `_vt` heals with a synthetic error result. Directly
  answers set-context goal (a)'s "tool call without its result" question.

### E3. Wire probes (API), p11+ in the existing harness style

Each probe: build a fixture jsonl, resume via SDK query() through the
recording shim, hard-assert on the captured outbound request (never model
recall). One run each unless an assert fails. Every fixture with a
boundary sets `uuids === allUuids` (the downstream re-insertion pass
prefers `allUuids`, so a mismatch confounds relink-then-expansion with
direct `allUuids` re-insertion). Fixtures pre-register the exact predicted
request under each competing model before running; unique content markers
per entry so assertions work at content-block granularity. Probe designs
are finalized AFTER E2a's call-graph answer (predictions depend on which
resume path is real). Run order: p13 first (the clean "is expansion active
on resume at all" control), then the boundary probes.

Budget as drafted: p11a/p11b/p12×2/p13/p14/p15a/p16-wire/p17 = 9 calls ≈
$0.09, plus the full E1 rerun (audit result: ≈48 live calls ≈ $0.50).
APPROVED by Anton 2026-08-29 (both; subscription-billed).

- **p13 in-turn fork on plain resume**: readonly-fold-shaped fixture (no
  boundary), plain resume; assert the request carries the off-path sibling
  tool_use + its result. Upgrades the earlier model-recall evidence to
  request-level: pins end-to-end same-message expansion on plain resume
  (behavior, not the `Aer` attribution — that needs E2a).
- **p11a partial-API-message playlist, text/thinking case**: an assistant
  turn split into thinking + text entries sharing one `message.id`, no
  tools; the playlist preserves the TEXT entry and excludes the thinking
  sibling (same model throughout, valid signed thinking — thinking-only
  preservation or cross-model stripping would confound). Isolates the
  expansion rule — no tool-pair machinery can mask it. Decides playlist
  closure for thinking/text siblings; p11a+p11b jointly inform the
  authoring rule for the shapes we've observed.
- **p11b partial-API-message playlist, parallel-tool case**: two same-id
  sibling tool_use entries, each with its own uniquely-marked tool_result
  user child; boundary preserves one sibling + its result only. Assert the
  off-playlist sibling and its result **separately** (partial recovery —
  sibling without result — is a distinct outcome). Together with p11a this
  gives the set-context authoring rule for the shapes we've actually seen;
  it does NOT establish every partial-API-message shape (malformed tool
  combinations etc. stay out of scope). Also run the identical fixture
  through getSessionMessages (free) for the consumer comparison P8 opened.
- **p12 consecutive-user retention**: boundary preserving [user A, user B,
  user C] adjacent (no assistant between), unique marker per message.
  Assert per marker: present/absent, block order, and API-message grouping
  (merge-without-loss is a distinct outcome from drop). Second variant
  with tool_result users — which MUST retain the corresponding assistant
  tool_use entries (unique tool_use_ids) so orphan-tool sanitization can't
  masquerade as consecutive-role normalization; assert by tool_use_id.
  Exploratory unless E2b pins the drop rule first; the original
  observation's exact shape is not recorded, so characterize, don't
  confirm.
- **p14 duplicate-uuid playlist**: P3 m4 asserted relink-skip on 2.1.195;
  `Kje` has no check (D4). The old m4 shape is non-discriminating — under
  an unchecked sequential rewrite of `[A,B,A,B]` the leaf walk can land on
  the summary and produce the same "summary only" observation as an
  explicit skip (the P1 d lesson again). New fixture: add a post-boundary
  anchor child so the models predict different parents — explicit skip
  leaves it under the anchor; unchecked rewrite reparents it to the
  duplicated-list tail. Pre-register both predicted request chains.
- **p15 stacked boundaries, sequential-all vs last-wins discriminator**
  (shapes per D2's consequence column): (a) valid boundary, then an INVALID
  boundary as the file's effective tail (no trailing summary/turn — the
  shape P1 d masked): three models, three predicted contexts (earlier chain
  / raw resurrection / empty). Control every candidate leaf and marker so
  synthetic insertions ("No response requested") can't blur which chain
  appeared. (b) anchor-child-catchment composition: NOT probed — it
  requires boundary 2's anchor on boundary 1's playlist, which lies outside
  the shapes native compaction and clauctl set-context produce (anchor
  after the boundary, playlist before it); record in FINDINGS as a scoped
  assumption about producers, not a format invariant — the loader accepts
  anywhere-in-file uuids and adversarial files can violate it.
  Deprioritize (a) too if E2c finds the resume path relinks
  last-boundary-only.
- **p16 cut-vs-no-cut (D3)**: post-boundary user/assistant entry whose raw
  parent is a non-preserved PRE-boundary entry, plus a control parented on
  the preserved tail. Old model (cut + orphan reparent): it attaches to the
  preserved tail. No-cut walk: it follows its raw parent and resurrects
  excluded history. Run through getSessionMessages first (free), then one
  wire call regardless of what E2 source reading says — wire stays the
  oracle for assistant context.

## Out of scope (follow-up specs, after findings convince the reviewer)

- clauctl code changes: whether `loadedContext` grows the expansion (and
  which consumers — TUI replay, set-context verification, get-messages
  synthesize, seed — want which granularity). The set-context spec's goals
  (Anton, 2026-08-28):
  - (a) predict what the assistant context actually ends up being after
    creating a boundary with given preserved uuids (consecutive user
    messages — do later ones drop? a tool call without its result — does it
    drop? one of two forked tool calls — what happens?);
  - (b) preserve user intent as well as possible — e.g. auto-include a tool
    call's result, auto-include same-turn (same `message.id`) entries when
    an assistant message is chosen, insert synthetic assistant messages
    ("No response requested") between requested consecutive user messages
    so the caller's chosen messages actually land in context.
  - Closure directive (Anton, 2026-08-29 live experiment, session ee0d):
    including a tool call silently inserts its result immediately after;
    including a result silently inserts its call immediately before; per
    E2a's cut-before-expansion, closure is at API-message granularity —
    an included entry pulls in all same-`message.id` siblings.
- TUI after set-context (Anton, 2026-08-29): (a) show a "context changed"
  marker live, not only on reattach; (b) render the playlist messages —
  after message surgery the user must be able to SEE the resulting
  context (single source of truth: render via the same loader code the
  estimate uses). Current behavior: stale pre-surgery messages, marker
  only after detach/reattach (/tmp/claude-tui-too-many-oks{,2}).
- Rewrite the probes as a rerunnable regression suite asserting our
  expectations, run as a standard part of SDK upgrades (Anton,
  2026-08-29).
- Blog post corrections (geraschenko.com claude-context).
